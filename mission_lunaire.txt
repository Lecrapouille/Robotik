C'est même un excellent démonstrateur pour RobotIK, car la mission Apollo 11 permet de mettre en œuvre presque toutes les notions que tu souhaites développer dans ta bibliothèque : robots, articulations, cinématique, dynamique, environnement, planification, tâches, compétences (skills), gestion des ressources et éventuellement IA.

Je te propose de ne pas chercher à reproduire fidèlement la physique spatiale d'Apollo 11. L'objectif serait plutôt de construire une simulation robotique et multi-agents d'une mission spatiale, avec une physique simplifiée mais des séquences opérationnelles réalistes.

Il y a une distinction importante à faire : une fusée n'est pas vraiment un robot articulé. En revanche, le module de commande, le module lunaire et leurs mécanismes peuvent être représentés comme des robots ou des systèmes mécatroniques. La mission, elle, peut être pilotée par ton système de planification.

# 3. La physique : ne pas chercher à tout simuler

C'est probablement la partie la plus délicate. Il existe plusieurs niveaux de fidélité.

| Niveau | Ce qu'on simule                            | Difficulté |
| ------ | ------------------------------------------ | ---------- |
| 1      | Trajectoires prédéfinies                   | Faible     |
| 2      | Propulsion, gravité et inertie simplifiées | Moyenne    |
| 3      | Mécanique orbitale réaliste                | Élevée     |
| 4      | Navigation et contrôle autonomes           | Élevée     |

Je te conseille de commencer par le niveau 2, avec quelques éléments du niveau 3.

Les notions physiques à connaître :

A. La gravité

La Terre et la Lune attirent les véhicules. La gravité lunaire est environ six fois plus faible que celle de la Terre.

Pour commencer, tu peux utiliser :

\\[ F_g = m \times g \\]

B. La propulsion

Un moteur produit une poussée dans une direction donnée.

\\[ F = \dot m \times v_e \\]

Avec :

- \\(F\\) : poussée du moteur.
- \\(\dot m\\) : débit massique du carburant.
- \\(v_e\\) : vitesse d'éjection des gaz.

Pour une première simulation, tu peux simplement définir une poussée constante et une consommation de carburant.

C. Le mouvement

Tu dois calculer la position et la vitesse en fonction des forces :

\\[ a = \frac{F\_{\text{total}}}{m} \\]

\\[ v\_{t+\Delta t} = v_t + a\Delta t \\]

\\[ p\_{t+\Delta t} = p_t + v\_{t+\Delta t}\Delta t \\]

C'est suffisant pour un premier modèle de vol simplifié.

D. Les orbites

C'est là qu'il y a une subtilité : aller vers la Lune ne consiste pas à pointer une fusée vers elle et à accélérer.

Il faut atteindre une vitesse et une trajectoire particulières. On utilise notamment des orbites elliptiques et des manœuvres de transfert.

Pour ta première version, tu peux utiliser des trajectoires orbitales prédéfinies, puis remplacer progressivement ces trajectoires par un calcul gravitationnel.

Je ferais donc deux simulateurs physiques distincts, partageant une même interface :

- Un simulateur orbital simplifié pour le voyage Terre-Lune.
- Un simulateur local pour les opérations proches de la surface lunaire : descente, atterrissage et décollage.

MuJoCo pourrait être particulièrement intéressant pour la seconde partie, notamment pour les contacts avec le sol, les pieds d'atterrissage et les mouvements du véhicule. Je ne chercherais pas à lui faire gérer toute la mécanique orbitale.

# 4. Le plus intéressant : piloter la mission avec RobotIK

C'est ici que ton projet peut devenir vraiment intéressant.

Tu as déjà les concepts de Mission, Task, Skill, Goal et Action. Apollo 11 est un excellent cas concret pour les mettre en pratique.

Je représenterais la mission ainsi :

## Mission Apollo 11

Mission globale

Goal : déposer les astronautes sur la Lune et les ramener sur Terre.

1. Task : Earth Launch
   - Skill : StartEngines
   - Skill : SeparateFirstStage
   - Skill : SeparateSecondStage
   - Skill : EnterEarthOrbit
2. Task : Trans Lunar Injection
   - Skill : OrientSpacecraft
   - Skill : ExecuteBurn
   - Skill : JettisonSIVB
3. Task : Docking
   - Skill : SeparateCSM
   - Skill : TurnAround
   - Skill : ApproachLM
   - Skill : Dock
4. Task : Lunar Orbit
   - Skill : LunarOrbitInsertion
   - Skill : OrbitCorrection
5. Task : Lunar Landing
   - Skill : UndockLM
   - Skill : DescentOrbitInsertion
   - Skill : PoweredDescent
   - Skill : Landing
6. Task : Lunar Ascent
   - Skill : StartAscentEngine
   - Skill : LeaveDescentStage
   - Skill : Rendezvous
   - Skill : Dock
7. Task : Return to Earth
   - Skill : TransferToCSM
   - Skill : JettisonLM
   - Skill : TransEarthInjection
   - Skill : EarthReentry
   - Skill : DeployParachutes

Attention à une subtilité : une Skill ne devrait pas être une simple animation.

Par exemple, `Dock` devrait être une véritable compétence qui :

1. Observe la position relative des deux véhicules.
2. Vérifie leur vitesse relative.
3. Oriente le véhicule.
4. Effectue une approche contrôlée.
5. Réalise le contact.
6. Verrouille les mécanismes d'amarrage.
7. Vérifie que l'amarrage est réussi.

Elle peut échouer, être interrompue ou nécessiter plusieurs tentatives.

C'est une bonne manière de tester ton système de Skills et de gestion des ressources.

C'est beaucoup plus intéressant architecturalement que de simplement animer une fusée qui monte.

Ensuite, tu construis les étapes précédentes et suivantes autour de cette fonctionnalité.

# 3. Concevoir les modèles physiques

## 3.1 Un modèle générique de corps spatial

Je créerais une abstraction `Spacecraft` ou, plus génériquement, `SpaceVehicle`.

Elle ne doit pas dépendre de la mission Apollo.

Par exemple :

```
struct SpacecraftState
{
    Position3 position;
    Orientation3 orientation;

    LinearVelocity3 linear_velocity;
    AngularVelocity3 angular_velocity;

    Mass mass;
};

class Spacecraft
{
public:
    SpacecraftState state() const;

    void apply_force(Force3 force);
    void apply_torque(Torque3 torque);

    void integrate(Duration dt);
};
```

Les types sont indicatifs : je réutiliserais tes types SI et tes conventions de RobotIK plutôt que de créer une seconde bibliothèque de quantités physiques.

Chaque véhicule possède des composants :

```
Spacecraft
 ├── RigidBody
 ├── MassProperties
 ├── PropulsionSystem
 │    ├── MainEngine
 │    └── ReactionControlSystem
 ├── FuelTank
 ├── NavigationSystem
 ├── Sensors
 └── DockingPort
```

Le moteur principal produit une poussée importante. Le RCS (Reaction Control System) utilise de petits propulseurs pour contrôler l'orientation et effectuer de petites corrections de trajectoire.

Tu pourras ensuite réutiliser ces composants pour d'autres véhicules.

## 3.3 Les deux moteurs physiques

Je définirais une interface commune :

```
class IPhysicsBackend
{
public:
    virtual ~IPhysicsBackend() = default;

    virtual void add_body(BodyDescription const&) = 0;
    virtual void remove_body(BodyId) = 0;

    virtual void apply_force(BodyId, Force3) = 0;
    virtual void apply_torque(BodyId, Torque3) = 0;

    virtual void step(Duration dt) = 0;

    virtual BodyState state(BodyId) const = 0;
};
```

Avec deux implémentations :

```
IPhysicsBackend
    |
    +-- OrbitalPhysicsBackend
    |
    +-- MuJoCoPhysicsBackend
```

Je ne ferais cependant pas semblant que les deux backends sont interchangeables dans tous les domaines.

Le backend orbital gère :

- La gravité terrestre et lunaire.
- Les trajectoires.
- Les accélérations dues aux moteurs.
- Les changements de masse.
- Les mouvements de translation et de rotation.

Le backend MuJoCo gère :

- Le contact des pieds avec le sol.
- La stabilité au toucher.
- Les irrégularités du terrain.
- Les collisions.
- Les mouvements mécaniques locaux.

### Comment passer d'un backend à l'autre ?

Je créerais un `PhysicsDomainManager`.

Il serait responsable des domaines physiques actifs et des transferts d'état.

```
Orbital Domain
      |
      | Enter landing simulation
      v
State Transfer
      |
      v
Lunar Surface Domain (MuJoCo)
      |
      | Takeoff / leave surface
      v
State Transfer
      |
      v
Orbital Domain
```

Il faut toutefois éviter de basculer tout le véhicule dans MuJoCo simplement parce qu'il approche de la Lune.

Je garderais la dynamique orbitale comme référence et utiliserais MuJoCo comme simulateur local de contact, avec un couplage explicite des forces et des états pendant la phase d'atterrissage.

C'est plus complexe qu'un simple transfert de position, mais cela évite les discontinuités physiques.

Pour une première version, un domaine local de contact simplifié avec gravité lunaire constante suffit.

## 3.4 Le moteur orbital

Pour commencer, je recommande un modèle gravitationnel à deux corps dominants :

\\[ \vec{F} = -\frac{GMm}{r^3}\vec{r} \\]

Tu calcules la gravité terrestre et lunaire séparément et tu additionnes les forces.

Ensuite :

\\[ m\vec{a} = \sum \vec{F} \\]

Tu ajoutes la poussée des moteurs.

Pour l'intégration numérique, je choisirais :

- RK4 pour commencer.
- Une intégration adaptative ultérieurement si nécessaire.
- Un pas de simulation indépendant du pas d'affichage.

Il n'est pas nécessaire de simuler chaque seconde de voyage en temps réel. Tu peux accélérer le temps de simulation.

Je distinguerais trois horloges :

| Horloge      | Fonction                            |
| ------------ | ----------------------------------- |
| Physics time | Intégration des équations physiques |
| Mission time | Temps écoulé depuis le décollage    |
| Wall clock   | Temps réel de l'application         |

C'est indispensable pour accélérer un voyage de plusieurs jours tout en conservant une simulation stable.

## 4.1 Une Skill doit être observable

Je garderais une interface de ce type, adaptée à ton système actuel :

```
class Skill
{

    virtual void start(Context&) = 0;
    virtual void update(Context&, Duration dt) = 0;
    virtual void cancel(Context&) = 0;

    virtual SkillStatus status() const = 0;

```

Avec des états explicites :

```
Idle
Running
Succeeded
Failed
Cancelled
```

Une Skill expose également :

- Ses préconditions.
- Ses effets.
- Ses ressources nécessaires.
- Ses paramètres.
- Ses observations.
- Ses conditions de succès et d'échec.

Par exemple, `Dock` peut réserver les ports d'amarrage des deux véhicules, utiliser les capteurs de navigation et réclamer l'autorisation du contrôleur de proximité.

# 5. La planification autonome

Je ne donnerais pas la totalité des 195 heures de mission à un planner PDDL.

Ce serait une mauvaise séparation des responsabilités.

Je ferais trois niveaux de décision.

Niveau 1

Mission Planner – PDDL / Prolog

Décide des objectifs et de l'ordre des grandes opérations.

Exemple : atteindre l'orbite lunaire avant d'autoriser la séparation du LM.

Niveau 2

Mission Runtime – Petri / GRAFCET

Gère les séquences, synchronisations, transitions, ressources et procédures de sécurité.

Niveau 3

Skill Controllers

Réalisent les opérations physiques en boucle fermée : orientation, poussée, approche, atterrissage.

### Exemple de domaine PDDL simplifié

Voici les prédicats que je définirais :

```
(:predicates
    (on-earth ?vehicle)
    (in-earth-orbit ?vehicle)
    (in-translunar-trajectory ?vehicle)
    (in-lunar-orbit ?vehicle)
    (landed-on-moon ?vehicle)

    (docked ?vehicle1 ?vehicle2)
    (separated ?vehicle1 ?vehicle2)

    (fuel-available ?vehicle)
    (mission-safe)
    (crew-transferred)
)
```

Une action conceptuelle :

```
(:action undock-lm
    :parameters (?csm ?lm)
    :precondition
        (and
            (docked ?csm ?lm)
            (in-lunar-orbit ?csm)
            (mission-safe)
        )
    :effect
        (and
            (separated ?csm ?lm)
            (not (docked ?csm ?lm))
        )
)
```

Le planner génère une séquence d'opérations. Le runtime vérifie que les conditions réelles permettent de les exécuter.

Important : les prédicats doivent provenir de l'état réel du simulateur, et non d'un scénario qui déclare arbitrairement qu'une opération est terminée.

Je garderais aussi les conditions de sécurité indépendantes du planner : un planner ne doit jamais pouvoir contourner une interdiction physique ou une condition d'abandon.

## 7.1 Configuration YAML

L'intérêt de ton approche est de pouvoir décrire les véhicules sans coder chaque configuration en C++.

Par exemple :

```
spacecraft:
  csm:
    name: Columbia
    mass: 28800
    propulsion:
      main_engine:
        thrust: 91000
      rcs:
        enabled: true

  lunar_module:
    name: Eagle

    stages:
      - name: descent
        mass: 10300
        engine:
          thrust: 45000

      - name: ascent
        mass: 4700
        engine:
          thrust: 16000
```

Valeurs illustratives et arrondies pour la structure du démonstrateur, pas une configuration de vol historiquement certifiée. Les masses et poussées devront être affinées avec les documents NASA.

Je ferais également une configuration pour les caractéristiques de la Terre, de la Lune, les conditions initiales et les paramètres de simulation.

# 8. Roadmap détaillée de développement

Je ferais le développement en 7 milestones. Chaque milestone doit produire quelque chose de fonctionnel et testable, sans attendre la mission complète.

## M0 — Fondations physiques

Priorité absolue

Objectif : créer un système de simulation de véhicules spatiaux génériques.

À développer :

- `Spacecraft` et `RigidBody`.
- Masse, inertie, position, orientation.
- Propulsion et consommation de carburant.
- Gravité et intégration numérique RK4.
- Temps de simulation accéléré.
- Backend orbital indépendant de MuJoCo.

Démonstrateur : un véhicule quitte une orbite terrestre, effectue une poussée et rejoint une autre trajectoire.

Critère de validation : conservation raisonnable de l'énergie sur une orbite sans propulsion et résultat reproductible.

## M1 — Véhicules et séparation

Objectif : construire les objets Apollo.

- Saturn V avec ses trois étages.
- CSM avec modules de commande et de service.
- LM avec étages de descente et de remontée.
- Système de séparation générique.
- Gestion de masse après séparation.
- Gestion des connexions entre véhicules.

Démonstrateur : une fusée décolle, largue ses étages et conserve un état physique cohérent.

## M2 — Rendez-vous et amarrage

Milestone architectural majeur

Objectif : deux véhicules autonomes savent se rejoindre.

- Port d'amarrage générique.
- Calcul de position relative.
- Contrôleur d'approche.
- Contrôleur de vitesse relative.
- Alignement des ports.
- Verrouillage mécanique.
- Désamarrage.

Démonstrateur : un CSM récupère un LM dans l'espace.

C'est le milestone que je considérerais comme le premier grand succès de RobotIK sur ce projet.

## M3 — Environnement lunaire

Objectif : réussir un atterrissage physique.

- Gravité lunaire.
- Terrain simple.
- Modèle local MuJoCo.
- Pieds d'atterrissage.
- Radar d'altitude simulé.
- Contrôleur de descente.
- Détection du contact.
- Stabilisation.

Démonstrateur : le LM se pose sur la Lune sans basculer.

## M4 — Mission autonome

Objectif : faire exécuter les opérations par RobotIK.

- Skills de propulsion.
- Skills de séparation.
- Skills de navigation.
- Skills de rendez-vous.
- Skills d'atterrissage.
- Domaine PDDL.
- GRAFCET de mission.
- Gestion des ressources.
- Gestion des erreurs et annulations.

Démonstrateur : un planificateur génère et exécute une mission lunaire simplifiée.

## M5 — Mission Apollo complète

Objectif : assembler les différentes phases.

- Décollage.
- Orbite terrestre.
- Injection translunaire.
- Transposition et amarrage.
- Mise en orbite lunaire.
- Séparation du LM.
- Alunissage.
- Décollage lunaire.
- Rendez-vous et amarrage.
- Retour terrestre.
- Rentrée et récupération.

Démonstrateur : mission complète Terre-Lune-Terre sans intervention humaine nominale.

## M6 — Supervision et expérimentation

Objectif : transformer le démonstrateur en laboratoire.

- Interface Compages.
- Timeline de mission.
- Visualisation des trajectoires.
- Tableau de bord télémétrique.
- Mode pause et reprise.
- Accélération temporelle.
- Injection de pannes.
- Rejeu déterministe.
- Comparaison des plans.
- Assertions automatiques.

# 9. Tests et validation : ne pas se contenter d'une belle animation

Je ferais de ce démonstrateur un banc de tests automatisés.

Voici les tests que je trouve importants :

| Test              | Assertion                                           |
| ----------------- | --------------------------------------------------- |
| Orbite circulaire | Le véhicule conserve approximativement son orbite   |
| Propulsion        | La vitesse augmente dans la direction attendue      |
| Carburant         | La masse diminue correctement                       |
| Séparation        | Les deux véhicules deviennent indépendants          |
| Amarrage          | La distance et la vitesse relative sont compatibles |
| Désamarrage       | Les véhicules peuvent s'éloigner                    |
| Atterrissage      | La vitesse verticale est faible au contact          |
| Stabilité         | Le LM ne bascule pas                                |
| Décollage lunaire | L'étage de remontée quitte la surface               |
| Rendez-vous       | Le LM rejoint le CSM                                |
| Mission           | Tous les objectifs finaux sont atteints             |

Je créerais également des scénarios d'échec :

- Panne du moteur principal.
- Quantité de carburant insuffisante.
- Échec de séparation.
- Erreur de navigation.
- Approche trop rapide lors de l'amarrage.
- Mauvaise orientation du LM.
- Atterrissage instable.
- Amarrage impossible après le décollage lunaire.

Cela permettra de vérifier que RobotIK sait planifier une récupération, et pas uniquement suivre un scénario heureux.

Un point important : le moteur orbital doit être déterministe autant que possible. Pour un même état initial, un même plan et une même séquence de commandes, les résultats doivent être reproductibles.

# 11. Mes recommandations architecturales finales

Il y a cinq décisions que je prendrais dès maintenant.

| Décision      | Recommandation                                          |
| ------------- | ------------------------------------------------------- |
| Physique      | Un moteur orbital générique indépendant de MuJoCo       |
| Véhicules     | Des corps rigides indépendants et composables           |
| Amarrage      | Une vraie Skill générique avec contrôleur de proximité  |
| Planification | PDDL pour les objectifs, Petri/GRAFCET pour l'exécution |
| Visualisation | Compages, sans dépendance du moteur physique            |

J'ajouterais trois fonctionnalités transversales qui pourront servir à beaucoup d'autres projets :

1\. Gestion des domaines physiques

Un système capable de représenter plusieurs environnements physiques et de gérer les transitions entre eux.

2\. Gestion des véhicules composés

Un système où plusieurs robots ou corps rigides peuvent être assemblés, désassemblés et transférés d'un état à un autre.

3\. Gestion des missions temporelles

Une mission possède une horloge, des événements, des délais, des interruptions, des échéances et des possibilités de reprise.

Ces trois fonctionnalités me semblent beaucoup plus intéressantes pour RobotIK que de développer des classes spécifiques à Apollo.

# 12. Ce que je développerais concrètement en premier

Je te propose un premier démonstrateur intermédiaire, avant même Saturn V.

# Apollo 11 – Prototype 0

[Apollo 11 50th Anniversary 2019 Model Kit Re-releases](https://images.openai.com/static-rsc-4/ViLO9B_QebVttnZuJZWlF0inW8yn4EFqZdIpuaUb8BdDv6XW2zepn87Q8KLREt_ojennZCbO-4sxCmpzYVCOPQkbVYqlfOz2Ts6LEAT1JHHplwrt3E7_rJc0bSi26xfo7fTU_EHKHRag_c4q1XBBIE-ZpjBMBdxPwzyN48ad-T4?purpose=inline)

[themodelstash.blogspot.com](https://themodelstash.blogspot.com/2019/02/apollo-11-50th-anniversary-model-kit-re.html?utm_source=chatgpt.com)

Scénario : deux véhicules dans l'espace

1. Le CSM et le LM apparaissent séparément.
2. Le CSM reçoit un objectif de rendez-vous.
3. RobotIK calcule un plan d'approche.
4. Le contrôleur corrige la vitesse et l'orientation.
5. Le CSM rejoint le LM.
6. La Skill `Dock` verrouille les deux véhicules.
7. Le planner constate que l'objectif est atteint.
8. Une autre Skill réalise le désamarrage.

Critères de réussite :

- Deux véhicules physiques indépendants.
- Aucun déplacement prédéfini ou animation forcée.
- Un contrôleur en boucle fermée.
- Un runtime autonome.
- Des assertions vérifiant le résultat.

Je choisirais ce prototype pour une raison : il valide simultanément le modèle de véhicule, la physique, les contrôleurs, les Skills, les ressources et le runtime.

Ensuite, j'ajouterais le LM et son atterrissage, puis le moteur orbital Terre-Lune et enfin Saturn V.

Mon avis architectural : Apollo 11 pourrait devenir l'un des meilleurs démonstrateurs de RobotIK, parce qu'il oblige à faire cohabiter trois mondes que tu développes actuellement séparément : la robotique, la planification et les systèmes à événements discrets.

Et surtout, tu obtiendras à terme quelque chose de réutilisable : une bibliothèque capable de simuler et de piloter des systèmes autonomes composés de plusieurs véhicules coopérants.
